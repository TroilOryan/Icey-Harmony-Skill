# 二进制资产（定长表）安全改动协议

适用于 `entry/src/main/resources/rawfile/` 下那些「每元素 N 个 float」的表，以及配套的索引表。
典型形态：

| 文件 | 形态 | 说明 |
|---|---|---|
| `stars.bin` | `Float32Array`，每元素 5 个分量 | ra, dec, mag, ci, conIdx |
| `lines.bin` | `Uint16Array`，两个一组 | 端点对（引用 stars.bin 的下标） |
| `meta.json` | JSON | `starCount`、以及散落在各处的下标字段（`"star": 12345`） |

风险不在数值本身，而在**下标**：删掉一条记录会让其后所有下标平移，而索引表默默指向错的目标——不报错、不越界，只是「星星连错了线」。

## 协议：先体检 → 断言安全 → 再动手 → 自检

### 0. 备份原始文件

```bash
cp entry/src/main/resources/rawfile/stars.bin .workbuddy/cache/stars.orig.bin
```

若项目有 git，`git show HEAD:<path>` 更可靠——但**先确认它真的是 git 仓库**（`git rev-parse HEAD`），
很多 ArkTS 工作目录并不是。这个备份必须在第一次覆盖前做：一旦没有版本控制又没有备份，
原始记录只能靠工具输出的逐行转储凑回来（本文档末尾有重建示例）。

### 1. 只读体检

```bash
node scripts/bin-table-audit.mjs <表文件> <每元素 float 数> <索引文件...> <meta.json>
```

看四块输出：

- **A 数值合法性**：整列 NaN（字段缺列）、零值占比过高（默认值填充）、量纲越界
- **B 来源指纹**：多来源拼接的表能靠指纹定位分界。按可靠性排序：
  1. **某列「恰好为 0」的逐窗口比例**（最稳）。典型症状：主段某列几乎不为 0（如色指数列零值 0.2%），补录段大面积是 0（72%）
  2. **坐标精度层级**（RA/Dec 只需 3 位小数 vs 需要 6 位）—— 注意主表内部小数位数本身就在 4/5/6 抖动，
     单看「众数突变」会误报，必须配第 1 条一起看
  3. **权重/星等列系统性偏移**（补录段恒偏暗 ~0.9 等）
  4. 脚本会额外打印**末尾 24 行逐行转储**——分界最直观的证据，同时这份转储本身就是备份
- **C 索引引用安全**：所有引用方（`Uint16Array` 索引表 + JSON 里的下标字段）的**最大下标**
- **D 近坐标重复分档**：区分「真重复」与「分量对」（见下方反例）

### 2. 断言索引安全（动手前的硬闸门）

设所有引用方的最大下标为 `refMax`。

- `refMax < 改动区间起点` → **安全**：只在 `refMax` 之后的区间增删，现有索引全部不变，**零重映射**
- 否则 → **危险**：必须重映射。做法：建 `keep = [保留的原下标...]`，
  再建 `newIndex[old] = keep.indexOf(old)`，然后
  1. 表本身按 `keep` 重排行
  2. 索引表每个端点过 `newIndex`，任一端点被剔除则**整条记录丢弃**（不要留悬空引用）
  3. JSON 里所有下标字段过 `newIndex`
  4. 丢弃的索引记录数要打印出来对比预期

把这条断言**写进脚本里**，不满足就 `throw`。靠人记着容易漏。

```js
if (refMax >= MAIN_END) throw new Error('索引引用越界，需重做映射逻辑');
```

### 3. 剔除 / 追加的两种安全操作

**剔除**（清理重复条目）：

```js
// 判据必须是「同一目标」而不是「坐标接近」——见下面的反例
const dup = [], keep = [];
for (let i = START; i < N; i++) {
  const m = nearestInRange(ra, dec, 0 /* 仅在 [0, START) 内找 */, 0.15);
  if (m.d < 0.15) dup.push(i); else keep.push(row(i));
}
```

**追加**（补回缺失记录）：直接 `push` 到表尾，`starCount = rows.length`，
JSON 里指向它的下标字段用 `rows.length - 1`。追加**永远不动已有下标**，是最安全的操作。

### 4. 自检（必须重读文件，不能复用内存态）

```js
const back = new Float32Array(readFileSync(out).buffer /* 注意 byteOffset */);
// 尺寸自洽
assert(back.length === newN * STRIDE);
// 末条 = 刚追加的记录
// 所有引用方下标 < newN
// 剔除判据复跑一遍，重复数应为 0
```

## 关键反例：看着像重复，其实是设计

`9943` / `9944` 两条坐标**完全相同**（0.0000°），权重 4.33 / 4.80。
按「同坐标即重复」的判据应该删掉较暗的一条——**但这是错的**：

- 4.33 与 4.80 两个分量换算合成星等 = `-2.5·log10(10^(-0.4·4.33) + 10^(-0.4·4.80)) = 3.79`
- 该位置的真实目标 ξ UMa（北斗六的对伴星）合成星等真值 **正好是 3.79**

即：这两条是**双星的两个分量**，数据是对的。同一张表的主段里 α Cen 也是这么存 A/B 两颗的（相距 0.0053°、相邻下标）。

**判据升级版**：

| 症状 | 判定 |
|---|---|
| 坐标几乎相同（<0.01°）+ **相邻下标** | 分量对，设计如此 → 保留 |
| 坐标几乎相同（<0.01°）+ 非相邻下标 + **权重差恒偏向一侧** + 来源指纹分属两段 | 真重复 → 剔除更差的那条 |
| 坐标差 0.02°~0.15° + 权重差任意 | 视场内普通邻近天体 → 保留 |

再加上来源指纹（`B` 段）：只有**跨来源段**的重合才值得怀疑。单一段内部的近坐标对基本都是真实天体。

## 改动后的依赖顺序

漏一步就静默失效（不报错，只是不生效）：

1. 表文件（`.bin`）
2. 索引文件（`.bin`）
3. JSON（`starCount` + 下标字段 + 任何按名索引的数组，如「要点亮的亮星名单」）
4. 源码里的名字映射表（英→中名这类），否则新记录会以原始英文名显示或干脆不显示
5. 版本号 / changelog

## 原始文件已丢失时的重建

若表被覆盖且无版本控制，可从工具输出的逐行转储重建——前提是之前打印过完整内容：

```
idx=9944 RA=169.547 Dec=31.529 mag=4.80 ci=0.00
```

用这些行拼回一个 `RESTORE` 数组参与判定即可。所以**体检脚本要默认打印全量分界附近的行**，这本身就是备份。
